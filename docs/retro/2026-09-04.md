Of five stories with both a registered estimate and a resolution on record, **three ran higher
(1.7x-4.3x), one ran lower (0.67x), and one was cancelled to zero.** The lower one matters more than
a single data point: `build_squad` was probed exactly like the others, and the probe found the fix
was *smaller* than the `(3)` anchor assumed — one guard at the top of the function, not the wider
duplicate-handling sweep the estimate had priced in. That is a materially different result from
"probing always finds more work": on this sprint's evidence, **probing corrects in both directions**,
which is the answer to the standing objection against a probe-first regime — that it would only ever
inflate scope. It doesn't, at least not here.

That still leaves the three upward misses unexplained, all made **after**
`dispatch-protocol.md` existed and probed first, distinct in kind from the
53k-token, 5-round pre-protocol migration's own class of failure (§3 below). Two readings are
available and `build_squad` weakens one of them: (a) the anchor set in
`docs/wiki/dispatch-protocol.md` rule 11 is mis-calibrated at the 3-5 band specifically — three of
four re-estimates in that band ran high, and the 13-anchor (the seven-model migration, "correctly
scoped") held; or (b) probing reliably finds *actual* scope, in whichever direction it lies, rather
than systematically inflating it — `build_squad`'s 3→2 is direct evidence for (b), since the same
`(3)` anchor produced both a 4.3x miss (MILP swap) and a correct-to-generous estimate (`build_squad`)
depending on what the probe found, not on any fixed bias in the anchor itself. Reading (b) is now the
better-supported of the two on this sprint's data: an anchor that were simply set too low at the 3-5
band would not also produce a downward correction starting from the same number. I still can't fully
settle it from five data points and one probe-first sprint — it is a question for the user in §5, not
a conclusion I'm asserting.

One thing the record does settle: **the probe-first rule changed *when* the correction landed, not
whether one was needed.** Every re-estimate above — up or down — was caught by a probe *before* the
dispatch that would have built the wrong-sized thing, not discovered mid-build the way RC1/RC2 were
in the pre-protocol migration. That is a real, measured behaviour change, distinct from the
estimation-accuracy question.

**Process finding, because it's the more valuable half of this correction:** estimates are
registered and re-estimated in `PROGRESS.md`, and the punch-card carries the *reasoning* for a
re-estimate but not the estimate pair itself — the `build_squad` row above was missed on first pass
because I searched `.punchcard/s006.jsonl` alone, which is exactly the failure mode CLAUDE.md warns
against for gate numbers ("indexes, not citation sources") applying one layer further back, to
estimates. `git log -S "<story text>" -- PROGRESS.md` is what actually found it.
**Recommendation:** punch-card the estimate pair at registration and at every re-estimate
(`{"event":"finding","what":"estimate 3 -> 2, reason: ..."}`, alongside the existing prose finding,
not instead of it) — that keeps the punch-card the single append-only source calibration work can
grep, rather than requiring `git log -S` over a file whose story text can itself be reworded between
commits (which would break a `-S` search silently, the same fragility as a literal-date test). Until
that's adopted, any future estimate-vs-actual analysis **must** run `git log -S` over `PROGRESS.md`
in addition to the punch-card, or it will systematically under-count the exact data it needs — as
this one did, on its first pass.

## 4. The Architect's own errors this sprint — not softened

All five are on the punch-card, verified independently, not accepted from the Architect's own
framing:

1. **Stale gate number quoted from prose.** The seven-model-migration brief pinned the gate at
   0.3392 log-loss / 0.1048 Brier, quoted from `HANDOFF.md`'s summary table, which predated the L2
   penalty-scaling fix. The coder's measured 0.3025/0.0945 was correct and nearly got recorded as a
   failure against the stale number (`.punchcard/s006.jsonl:16`).
2. **Hollow verification of the bonus `minutes_frac` guard.** First attack constructed
   `BonusPlayerInput` missing two required arguments, so both branches raised `TypeError` for the
   wrong reason and nearly got logged as "guard fires (correct)." Redone with the full signature,
   proven genuinely in both directions (`.punchcard/s006.jsonl:102`).
3. **A future-informs-past DC leak in the gate runner's cold-start fallback**, reusing a DC model
   fitted `as_of=now()` for a 2025-26 GW1 backtest. Caught and fixed *before* the recorded gate run,
   with a measured 90→85 behavioural proof and an unreachability attack (raises if the leaky path is
   ever called) — detail at `docs/retro/2026-09-03.md` §1.
4. **An unconditional `rm` destroyed 8 punch-card events.** Recovering an agent's mangled-filename
   punch-card write, the delete sat on its own line rather than chained to the success of the
   python step that made it safe, so it ran even after python failed. The 8 events were reconstructed
   from a 200-character-truncated display, not recovered verbatim (`.punchcard/s006.jsonl:212`).
5. **A piped gate command reported a false green.** `CLAUDE.md` names this exact failure mode from
   an earlier session (s003) — piping the measured command through `tail` makes `$?` report the last
   command's exit status, not the one being measured. Reproduced it here; caught only because the
   traceback happened to be visible in the captured output (`.punchcard/s006.jsonl:186`).

Two of these (1, 2) are exactly the class of mistake `dispatch-protocol.md` rule 2 and rule 4 exist
to prevent, committed by the author of those rules. Two (4, 5) are the exact incidents `CLAUDE.md`
already names from earlier sessions, reproduced despite the standing warning. None were self-caught
before an external check (an agent's contradicting evidence, or a visible traceback) surfaced them.
